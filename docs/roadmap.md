# characters 路线图

版本：v0.2，2026-11-05。本文是项目目标与后续里程碑，不是已实现状态；实现状态只在[实现状态](status.md)维护。本文中的命令、字段与流程在实现前都不是当前能力。第四节事项已于 2026-11-05 按建议确定，R0 已完成。

## 一、现状评估

### 已经成立的部分

- 产品边界清楚：管理服务不调用模型、不托管聊天；记忆须经管理端人工审核；没有进程级“当前角色”；角色启停只作用于绑定线程。这些约束继续保留。
- M1–M4 已实现：约 1 万行 TypeScript、31 份 schema，事务与中断恢复、请求去重、撤销、跨工作区/角色/项目隔离均有回归。
- dsh 0.2.1-rc.3 实际桌面端在显式 relaxed 合成实验中完成了加载、候选、确认、新会话命中、撤回后不命中的闭环，见 [dsh.md](dsh.md)。

### 主要问题

1. **主线多次变化，完成标准未同步。** 2026-10-25 由写作执行主线转为“服务 + Codex 插件”，10-27 暂缓 Codex、转向 dsh 与参考客户端，10-30 增加 Koto 长期相处验收。phase-1.md 的阶段完成标准仍要求“至少一个实际 Codex CLI 版本通过本会话隔离检查”（R0 已改写）。
2. **strict 是项目自身无法推进的门槛。** strict 需要可信验证器证明宿主本会话的全局记忆读取与生成均已关闭。M0 证实普通 Codex 插件拿不到这种控制；dsh 也尚无生产验证器。M5/M6 因此可能长期停在“未完成”，阶段无法收口。
3. **角色体验是最弱的一环。** 见 [Koto 长期相处验收](koto-long-term-acceptance.md) 的缺口分析：
   - 正反例被打包并参与摘要，但不在 context.get 交付项中；
   - `packages/core/src/knowledge.ts` 的检索按空白分词后做子串匹配，中文整句查询基本不会命中；
   - 无查询时默认交付按 ID 顺序取前 32 条可见记忆，与相关性和时间无关；
   - 参考客户端 `/remember` 不能传 replaces，用户入口无法完成原子纠正；
   - 参考客户端不能选择 mode；主要闭环测试的主体是 Kurisu，不是 Koto。
4. **日常使用摩擦过大。** dsh 每个新会话都要取得真实会话 ID，再执行 `connection grant` 与 `gateway pair`；授权 TTL 最长 3600 秒，绑定最长 60 分钟且不续期。安全上成立，但无法支撑持续数周的相处。
5. **状态描述分散。** 同一实现状态在 README、design、contracts、phase-1 中重复描述并附带大量限定，方向调整时难以全部同步，问题 1 即由此产生（R0 已集中到 status.md）。

## 二、目标

### 北极星

> 用户在一个真实宿主中与 Koto 持续相处 4 周以上：表达稳定、有判断，能用上用户批准过的共同经历，能被纠正，也清楚自己不记得什么；记忆的来源、审核、替代与撤回全程可解释。

衡量标准是真实使用与体验质量，而不是协议测试数量或 strict 是否通过。

### 保留的硬约束

- 管理服务不需要模型凭证，不建立 agent 推理循环。
- 记忆只由用户在管理端审核；agent 不能批准记忆、修改设定或扩大自身权限。
- 角色启停只影响其绑定线程，不改全局/项目插件开关、共享配置或其他会话的记忆模式。
- 不把角色设定写入宿主全局记忆、全局人格或项目 AGENTS.md。
- 不静默降级 strict；relaxed 只能由用户在管理端对单个授权显式选择，agent 和插件不能选择。

### 明确不做

向量检索、自动记忆抽取、多 agent 编排、市场、云同步、远程多用户、自动发布，以及以 Codex strict 为近期攻坚目标。需要时单独决定。

### strict 的新定位

strict 从“第一阶段完成条件”调整为独立的“宿主隔离认证”线：按宿主、按版本分别给出通过、失败或受阻的结论，结果记录在[实现状态](status.md#宿主隔离认证)。未认证宿主默认仍拒绝 strict 绑定；用户可对单个授权显式选择 relaxed，包括使用真实私人记忆，这是用户知情的风险选择，结果如实标注“relaxed 下使用”，不能改写为 strict 通过。design.md 与 contracts.md 已按此更新。

## 三、里程碑

### R1：Koto 体验基线（无模型）

- [ ] Koto 专属 K01–K08 合成请求捕获与结果记录模板；复用公开 RPC、模拟模型与临时目录。
- [ ] 中文检索：使用 Node 内置 `Intl.Segmenter`（zh，word 粒度）或二元分词，不引入新依赖；排序保持确定、可解释。
- [ ] K11 量化：40 条唯一主题合成记忆下，记录默认交付排除项、关键词命中与改写查询漏召回。
- [ ] 默认交付选择由按 ID 改为可解释的规则（例如按确认时间或用户置顶），排除理由写入交付清单。
- [ ] 正反例交付作为受预算约束的可选项，支持有/无示例对照；涉及 schema 时显式升版并迁移。
- [ ] 参考客户端 `/remember` 支持 replaces、kind 与 tags，并显示真实 ID/revision；管理审核仍独立，需要双方 revision。
- [ ] 参考客户端支持选择并显示 mode（conversation / coauthor）。

退出条件：K01–K08 的数据/协议路径全部通过；K09、K12、K14 的程序边界通过；K11 有量化报告。仍不代表角色表现或宿主隔离已验收。

### R2：真实相处试用（需单独授权，2–4 周）

- [ ] 选定日常宿主（见第四节）并记录宿主、插件、模型与配置版本。
- [ ] 在新的显式实验工作区按 [Koto 长期相处验收](koto-long-term-acceptance.md) 执行 K01–K08，按四项 0/1/2 评分，每个表达检查点重复 3 次。
- [ ] 记录使用数据：每周候选数、审核耗时、纠正与撤回次数、检索失败与漏召回案例。
- [ ] 输出“真实使用发现”清单，作为 R3/R4/R5 的排序依据。

退出条件：K01–K08 达到验收文档的评分门槛；数据/协议、角色表现、真实宿主三层结果分别记录，未运行项标“未执行”，缺宿主证据标“受阻”。

### R3：宿主接入可用性（dsh 优先）

- [ ] 常驻授权设计：按宿主 + 项目一次批准，授权范围内的新原生会话自动配对，期限更长且可续期；撤销、审计、逐线程隔离与 strict 规则不变。属于契约变更，先更新 contracts.md 与 schema。
- [ ] 调查 dsh 实际的跨会话记忆与持久化行为。若该版本没有全局记忆功能，评估以“宿主版本 + 二进制摘要 + 配置摘要”构成的静态能力档案作为可信验证器的可行性。
- [ ] 补齐正常关闭尽力结束绑定、强制中断依赖期限或撤销的实际宿主验证。
- [ ] relaxed 授权记录具体缺项：当前只记录 isolation=relaxed 与绑定的 isolationEffective，宿主能力档案出现后在授权与审计中写明未满足的条件。

退出条件：新建 dsh 会话加载 Koto 时，除首次授权外不需要 CLI 操作；strict 通过，或写明具体阻塞项，并保持默认拒绝。

### R4：管理 GUI（审核为主）

前提：R2 数据显示 CLI 审核是主要瓶颈。

- [ ] 记忆审核收件箱：候选、来源摘录、确认/拒绝/替代/撤回。
- [ ] 交付解释（context explain）与授权、绑定管理。
- [ ] 浏览器授权单独设计；不提供聊天界面、模型配置或任务执行台。

### R5：角色演进与扩展

- [ ] 角色包显式升级：版本差异、回滚和记忆兼容审查；不覆盖安装快照，不悄悄改写记忆。
- [ ] 用户审阅后的多来源总结提交（保留支持摘录与推断标识，不在服务中运行模型）。
- [ ] 第二个角色的长期验收或第二个宿主接入；Codex 在此阶段依据当时的宿主能力重新评估。

## 五、复杂度约束

- R2 之前不新增协议操作或持久 schema，除非 R1 清单明确需要。
- 每个里程碑先写退出条件，再实现；“协议测试通过”“工具接入可用”“角色表现通过”“宿主 strict 通过”分别记录，不能互相替代。
- 常规测试只使用临时工作区、假凭证与模拟服务；真实模型和真实宿主验收需用户单独授权。
