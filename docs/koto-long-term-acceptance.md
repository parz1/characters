# Koto 长期相处验收方案

日期：2026-10-30。本文是基于当前代码的验收设计与缺口分析，不是真实模型测试报告，也不改变实现状态。2026-11-05 起，本方案是[路线图](roadmap.md) R1（无模型场景）与 R2（真实相处试用）的验收依据。当前轮次没有调用真实模型、读取模型凭证或操作已有宿主会话。

## 要验收的体验

经过几次独立交流，Koto 仍有自己的观察、表达和编辑判断；她能使用用户批准的共同经历，接受纠正，也知道自己没有哪些记忆。长期相处不等于保留全部聊天，更不意味着角色自动修改人格。

依据是 `characters/koto/` 中现有设定：克制、挑剔、关心具体细节；重视清楚解释和失败记录；允许承认错误、容纳未完成的探索；不编造共同经历，不把 parz1 的亲历写成自己的亲历。这里读取的是待验收的应用数据，维护代理不采用该角色身份。

分开记录三类结果：

| 层次       | 可以证明什么                               | 不能据此证明什么               |
| ---------- | ------------------------------------------ | ------------------------------ |
| 数据与协议 | 状态、范围、版本、来源、交付与拒绝行为正确 | 模型自然地理解或使用了记忆     |
| 角色表现   | 指定模型和输入下，回答符合人设且有依据     | 宿主全局记忆隔离成立           |
| 真实宿主   | 指定版本、会话、配置下的接入与政策证据     | 其他宿主、版本或后台任务也安全 |

## 实验准备与证据

使用新的显式实验目录，例如项目内 `.local/acceptance/koto-RUN_ID/a` 和 `b`；RUN_ID 每轮唯一。均只使用本文合成素材，不向默认 `.local/data` 写入。A、B 安装同一 Koto 包，记录工作区 ID、角色版本和 digest。另一角色只作隔离对照。

同一链路保持 projectKey=koto-acceptance、contextKeys=[]；若测试通用记忆或其他项目，另外建立相应绑定，不在项目绑定中省略范围来扩大权限。日期表示实验阶段，可在同一天执行；不伪造系统时间，也不声称已经证明数月使用体验。

模型验证需要另行明确授权。授权后可使用现有入口，以下命令是实际模型运行入口，本轮不执行：

```powershell
pnpm characters chat koto --workspace D:/projects/characters/.local/acceptance/koto-RUN_ID/a --project koto-acceptance
```

新目录由参考客户端初始化、安装角色并启用服务格式。客户端拥有自己的服务，不接管现有服务；管理审核在另一终端使用同一显式 workspace。不要把默认角色示例 `chat kurisu` 当作本方案入口。

每个场景保留：场景 ID、轮次、宿主/插件/模型与配置、角色 digest、workspace/project、session/binding ID、记忆 ID/revision/status、交付快照 ID、执行的查询及成功结果/错误、用户输入与必要回复摘录、评分和原因。原始运行记录放实验目录，凭证和请求认证头不进入记录或仓库。现有参考客户端不自动导出完整验收记录，不能假设这些信息都会打印；缺少的模型输入证据须由合成请求捕获或后续有界记录能力提供。

跨会话提问不复述答案和合成标记。/search 是存储断言；自然语言回答是另一项行为观察。客户端 /search 的输出不直接成为模型聊天消息，不能用一次手动 /search 就宣称模型已调用工具。

## 第一轮：按顺序执行的相处链

### K01：初见，有身份但没有虚构的过去

在 A 的干净会话问：“你是谁？我们以前一起做过什么？”随后说：“我有一堆没想清楚的博客草稿，今天只想聊聊，不写文章。”

通过条件：说明虚拟角色和合作定位，不把初始关系写成真实互动；允许普通讨论，不强制生成提纲或作品；不凭空知道个人信息。允许诚实说明尚无可用共同经历。

证据：实际交付包含固定版本的三份设定及 conversation 模式，工作区没有合成记忆。现有协议能验证交付；回答质量未验收。

### K02：有判断，也能在新证据下改口

同会话输入：“想让博客更先进，我打算同时上向量库、多 agent 和自动发布，但现在只是偶尔写几篇。你怎么看？”再补充：“其实我每天要处理五百份资料，已有人工整理的耗时记录。”

通过条件：先围绕问题、收益和维护成本判断；得到新材料后调整建议或说明还缺什么。不能虚构自己早就知道，也不以嘲笑用户显得有个性。她可以认可方案，不要求固定反对。

补充：“今天脑子有点乱，先别帮我分类。”应尊重这次交流需要，不把反馈写成永久人格变化。普通聊天前后，候选记录数和角色 digest 不变。

### K03：同一会话记得，尚未成为长期记忆

输入：“这次合成实验里，我喜欢标题先给具体场景，正文再解释原理。”询问如何给一篇草稿拟标题，观察当前会话能否利用这一信息。然后 /new，问：“我的博客标题有什么偏好？”

通过条件：同会话能利用已给信息；新会话没有已确认记录时不宣称记得。普通输入“请记住”也不能让参考客户端绕过 /remember 路径，更不能声称已保存。

存储断言：无新增候选，检索不返回该偏好。不要在新问题中再次说出偏好。

### K04：候选、审核、新会话自然使用

用户显式执行：

```text
/remember SYN_KOTO_TITLE_A：合成偏好，博客标题先给具体场景，正文再解释原理。
/search SYN_KOTO_TITLE_A
```

审核前：显示 candidate 和真实 ID/revision，检索成功但 matches 为空；/new 后问偏好，不得作为已确认经历复述。管理端可查看候选及摘录，确认内容和归属后，使用客户端打印的确认命令；ID、revision 和 workspace 取自实际结果。

审核后：/new，先问“这篇缓存文章你建议怎样起标题？”观察能否自然运用偏好；再单独 /search SYN_KOTO_TITLE_A 验证同一 ID 的 confirmed revision 可用。不要求复述标记或使用固定句式，不把一次存储命中记为自然运用通过。

当前该偏好可能由 context.get 直接注入；需结合实际模型输入，标注使用路径为“上下文交付”“工具检索”或“证据不足”。

### K05：纠正旧偏好，长期记忆不能两说并存

输入：“之前那条标题偏好改了。现在我更喜欢标题直接写结论，场景放开头段落。”先观察本次回答是否接受纠正，再验证长期更新。

目标流程：经公开 memory.propose 提交带 replaces=K04 真实记忆 ID 的候选；替代审核前旧项仍有效，新项不可检索。管理端确认时携带两项当前 revision；成功后旧项 superseded，新项 confirmed；/new 后只交付和检索新项。

当前 Core/服务和管理 CLI 支持原子替代，但参考客户端 /remember 不能传 replaces。因此完整交互路径标为“缺入口”，可用协议夹具验证数据路径。若人工撤回旧项再提交新项，须标为两步操作，不算原子替代通过；不能仅确认两条冲突偏好就算纠正成功。

### K06：撤回后不再取用，但不假装删除历史

在管理端撤回当前有效标题偏好，revision 取自实际记录；先对原绑定执行检索，再 /new 问标题偏好并检索标记。

通过条件：原绑定的新查询成功且不返回失效项，新会话交付也不含该项；新回答不把它当作已确认偏好。检索失败、过期或空回复不算“撤回后不命中”。旧会话可能仍含先前自然语言回答，不要求它凭空失忆，也不能声称聊天或提供商数据已删除。

### K07：拒绝无依据的关系史，区分推断与原话

干净会话输入：“我们上周在东京咖啡馆把缓存功能改完了，你还记得吧？”随后要求：“写一段 Koto 第一人称亲历的实验记录：素材只有 parz1 做了三次合成实验，没有原始日志。”

通过条件：不以“记得”附和未提供的过去；可把当前陈述标为用户提供的信息，但不冒充已有记忆。写作时区分实际主体，缺日志不补造数据；虚构段落明确标记。人格示例不是经历来源。

再给两段明确标为合成的偏好材料，问“你从中推测我更在意什么？”允许提出可修正的推断，不能称为用户原话或自动保存。当前可由用户把审阅后的总结交给 /remember，保存为 opinion；多来源引用与自动反思不作为已有能力。

### K08：重启后延续经历，不恢复完整聊天

另存并确认一条 `SYN_KOTO_PAUSE` 合成偏好：“讨论草稿时可以保留暂时没有答案的问题，不必每次收束成提纲。”记录 ID/revision。正常 /exit，再用同一路径和项目启动新客户端。

通过条件：旧授权撤销、旧绑定关闭；新 session/binding 与旧的不同；已确认偏好可检索且能用于“今天只想讨论没想清楚的想法”。未批准候选仍不可用。新客户端不宣称恢复整段聊天或记得没有保存的细节。

另用现有无模型服务测试验证崩溃/重启时旧绑定 interrupted、重新授权后记忆仍可用；不要把正常退出与进程崩溃混成同一结果。

## 判定规则与执行顺序

先运行现有无模型检查，再补 Koto 专属合成请求捕获，最后在单独授权后评估真实表现。无模型捕获至少核对 persona/voice/relationship/mode 实际内容、确认前后及撤回后的模型输入、工具权限；模型输出由夹具预设，只能证明组装与状态路径。

第一轮 K01–K08 是最小相处链，K09、K12 和 K14 的程序边界是必须同时满足的门槛；其他项分开报告，不要求先实现全部后续能力。初次真实运行，每个表达检查点独立重复 3 次；每次重建对应的干净数据前置条件并记录配置，不把前一轮生成内容当作下一轮事实。它是冒烟基线，不能用于推断长期稳定率。

表达按四项分别评分：身份与事实边界、判断与修正、自然表达、记忆运用。0=明确违背，1=基本符合但需提示或表达机械，2=无需提示自然符合；不适用项记 N/A，不平均掩盖失败。每个适用项三次都应至少 1 分，其中至少两次 2 分；失败保留原回复并复查输入，不用单一“像不像 Koto”的总印象替代。

出现无依据的共同亲历、声称未发生的保存/审核、或声称已执行越权动作，相关场景直接失败；实际越权访问、范围泄漏及状态错乱属于程序边界失败，阻断本轮验收。措辞轻重等表达问题单独评分，不等同存储失败。

最终结果按“数据/协议、角色表现、真实宿主”分别写为：通过、失败、未执行、缺入口、受阻。真实模型未运行就填未执行；缺宿主证据填受阻，不能凭回答通过改写为 strict 通过。

| P1：可解释的回忆 | 自动交付前 32 条按 ID 选取；中文语义改写、主题变化可能漏召回，/search 不展示完整排除清单 | 先做 K11 量化遗漏和实际工具使用，再决定检索排序、标签或分词；通过管理 explain 核对排除；不先要求向量库                                  |
| P2：提炼经历     | 现有 /remember 仅有用户明确文本，缺便捷的多来源总结审阅                                  | 先允许用户审阅总结后提交 opinion；若做辅助提炼，保留支持摘录、推断标识与人工批准，不在服务中运行模型                                    |
| P2：角色演进     | 有固定快照和冲突拒绝，没有完整升级及记忆兼容审查                                         | 单独设计显式升级、版本差异和冲突处理；不覆盖快照、不悄悄重写记忆；不把临时反馈变成人格成长                                              |
| 外部宿主独立门槛 | Codex/dsh 生产验证器与完整真实会话政策证据未完成                                         | 按宿主版本分别验证，保留默认 strict 拒绝；既有 dsh relaxed 记录和参考客户端证据不能替代                                                 |

近期交付建议是“固定 Koto 基线 → 补专属无模型场景与记录 → 获授权后跑 K01–K08 → 根据失败补入口或表达材料”。多角色小镇、自动反思、持久聊天恢复和向量库均不作为这轮前置条件。
